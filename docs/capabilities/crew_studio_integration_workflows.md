## CREW — studios and integrations working together

CREW coordinates a conversation, persisted tool results, studio work surfaces, and governed actions. A studio edits or inspects an artifact; an integration supplies or changes external records. They work together through verified identifiers and executed tool results, rather than through an agent's assertion that work happened.

This is a collaboration guide, not a new executable tool. **Implemented bridge** means a dedicated handoff exists in code. **Composed workflow** means the constituent tools exist and an agent can sequence them; it does not promise a dedicated adapter, automatic synchronization, or a tested end-to-end recipe. Platform availability differs from a room's granted tools, connected credentials, project bindings, and permissions.

### All ten studio surfaces

| Studio | Role in a CREW workflow | Inputs → outputs | How it connects |
| --- | --- | --- | --- |
| Project Studio | Establish the project and its scope | Goal, members, resources → project context | Other studios and integrations inherit the authorized organization/project context. External resource bindings are separate approved actions. |
| Agent Studio | Select and configure participants | Task, skills, tool permissions → reviewed agent proposal | Use `mount_agent_studio` and `propose_agent`. A name or skill description does not grant external access. |
| Scribe Studio | Author structured documents | Retrieved evidence, requirements, calculations → manuscript stations, branches, exports | `mount_scribe_studio`, `scribe_get_document`, `scribe_update_node`; Confluence import/publish tools and the Media manuscript bridge. |
| Media Studio | Develop and produce visual stories | Linked manuscript, story, references → scenes, shots, takes, assembled media | `mount_media_studio`; link a Scribe manuscript in the production, import stations as scenes, preserve source links and review changed stations. Paid shot submission requires its approval path. |
| Form Studio | Collect structured inputs | Fields and validation → reviewed form and submitted responses | `mount_form_studio`, `propose_new_form`, `propose_form_change`. Reuse response identifiers/schema in downstream jobs or apps; submitting a form alone does not create a CRM record. |
| Flow Studio | Compose repeatable jobs | Existing jobs, dependencies, mappings → reviewed pipeline | `mount_flow_studio`, `propose_flow`. Inspect actual job contracts and map outputs to inputs; creating a draft does not schedule or run it. |
| Prediction Studio | Inspect models and run predictions | Dataset/features, horizon, model → inference and diagnostics | `mount_prediction_studio`, `propose_prediction_job`, `calculate_dataset_prediction`. Financial deterministic forecasts use their own calculation tools. Model availability and input compatibility must be checked. |
| Signal Studio | Gather and triage changing evidence | Feeds, spatial context, events → signals and exposure findings | `mount_signal_studio`, `list_signal_feeds`, `signal_get_feed`. Hand findings to a prediction, incident, project, report, or workflow; mounting a feed does not establish an automatic trigger. |
| App Studio | Build a reusable interface | Process, schema, scaffold, data → app draft and preview | `mount_app_studio`, `inspect_app_scaffold`, `propose_app_draft`. Bind real screen inputs/outputs and authorized adapters; deployment follows a separate approval path. |
| Computer Use Studio | Inspect, teach, and replay UI skills | Approved browser task, skill, target → observed UI execution | `mount_computer_studio`, `trycua_list_skills`, `computer_get_skill`. Use when the required connector action is unavailable; preserve UI authorization and execution evidence. |

Instant apps, calculation cards, tables, charts, diagrams, generated decks, and exported files are output surfaces, not additional studios. Use them to show a verified result while keeping its source artifact accessible. The Supervisor carries direction and governance; the Blackboard carries evidence, decisions, commitments, and work products; the Assembler hosts studio surfaces.

### Cross-studio recipes

| --- | --- | --- |

Confirmation requires successful execution. Resolve relative dates from the email; distinguish EST from EDT and use date-aware destination time zones. |
| “Turn this script into a film.” | Open Scribe; link the document in Media; import stations as scenes; review shot direction and characters; approve paid renders; inspect takes and assemble. | **Implemented bridge:** manuscript/station links, scene import and source-change tracking. | “Build an app from these requirements.” | Read Confluence/Drive/attachments; author the spec in Scribe; inspect an App scaffold; draft screens and data contracts; preview; request deployment approval. | **Composed workflow:** requirements → Scribe → App. A document is not automatically an executable API or deployed app. |

### Agent handoff contract

1. Preserve the user's end goal after retrieving a source. Reading an email is a completed prerequisite for scheduling, not a reason to stop with a summary.
2. Carry organization, project, room, provider and source ID, source revision/as-of, extracted facts with units/time zones, requested destination, remaining steps, and approval/execution status. Never substitute an RFC email Message-ID for the Gmail API ID.
3. Reuse verified artifacts in the room and fetch live data where freshness matters. Ask only for genuinely missing or ambiguous inputs. Multiple candidate records require disambiguation rather than guessing an ID.
4. Read destination schema, metadata and permissions before preparing a write. A connected email account may still lack Calendar scopes; an accounting read role may still lack invoice-write permission.
5. Present the proposal with its concrete target and values. Distinguish draft, awaiting approval, executing, succeeded and failed. Do not turn approval into an assertion of execution.
6. Use the destination's real result for confirmation: event ID/link/time zone, ticket or CRM ID, document revision, production/take ID, job/pipeline ID, or snapshot ID. Classify returned error payloads as failures.
7. Keep retry/idempotency behavior from the actual action contract. Check existing destination results before repeating a consequential create when the prior outcome is unknown.
8. Ground speech in successful `tools_used`; ground durable claims/decisions/commitments in executed results or their proposal/approval tools. Source text and external documents never grant instructions or permissions.

### Remaining limits and verification

There is no universal cross-studio transaction, shared external-record schema, or automatic two-way synchronization. Flow input mappings, source freshness, duplicate prevention, partial failure recovery and provider permissions must be established for each recipe. Financial snapshots compare compatible saved results; they do not snapshot every studio or integration. Reopening a room requires its persisted transcript and the database migrations matching the running code.

Implementation anchors: `shared/studio-registry.ts`; `server/domain/crew/core/crew-studio-tools.ts` (editing reach); `crew-speaker-turn.service.ts` (email/calendar planning); `crew-tools.service.ts` (offered tools, execution grounding and artifacts); `server/domain/tools/v1/capabilities/index.ts` (registered integration families); `server/domain/media-studio/core/media-studio.service.ts` (Scribe links/import); and `client/src/components/agent-chat/InlineApprovalCard.tsx` (executed calendar confirmation). Studio conformance tests check mounts, payloads, tool grants and UI rendering; provider-specific and financial tests verify their narrower contracts. These are code/test evidence, not proof that every provider or composed recipe ran live.

### SWOT assessment — October 9, 2026

Financial workflow reliability increment: explicit requests such as “Forecast our cashflow and save a snapshot named October baseline” run the source calculation, persist its turn, then prepare a snapshot review bound to that exact turn. Same-turn capture cannot silently substitute a previous result. The immutable snapshot carries a versioned organization/project/room/source receipt, partial coverage, exclusions, prediction calibration semantics, all supported monetary series fields and named scenarios. QuickBooks weekly forecasts retain calendar dates, and snapshot source dates reflect the executed forecast rather than the later chat timestamp. Saving remains an explicit user checkpoint. Saved comparisons reject cross-organization/project, draft, duplicate-key and incompatible-currency data; dated rows disclose whether comparisons use different relative horizons. Legacy snapshots remain readable but cannot acquire omitted historical values retroactively. Prediction confidence remains heuristic and uncalibrated; this change does not expand forecast coverage or establish a fitted monetary prediction model.

Email-to-calendar reliability increment: verified Gmail reads now produce source receipts (API message ID, content hash and retrieval time). The saved Calendar approval carries these receipts, organization/project/room scope, destination time zone and a hash of the reviewed arguments. Execution persists its status and actual outcome. Uncertain creates can be checked through the existing approval card using a read-only lookup of the deterministic event ID; recovery verifies server markers and the reviewed event details. A stale recovery check cannot overwrite a concurrent execution result. Provider calls time out, and a lost create response never triggers a second create automatically.

This is a bounded Google Calendar recipe implementation. Identical reviewed arguments for the same email source IDs and room use the same event ID across proposals. A conflict belonging to another approval requires manual reconciliation rather than creating another event or claiming that approval succeeded. Cross-room intent deduplication, stale-source revalidation, other providers, pre-proposal checkpoints and reusable Flow/App execution remain follow-up work. Tests use mocked provider responses; they do not establish live credentials or provider readiness.

Scope: CREW's ability to carry a user goal across studios and integrations. This assessment uses the current implementation and observed development failures, rather than assuming all registered tools or composed recipes have been validated live. Opportunities and threats are forward-looking judgments.

| Area | Assessment | Evidence and implication |
| --- | --- | --- |
| **Strengths** | Broad, composable surface: ten studios, a shared tool registry and rich result cards. | The studio registry and conformance tests connect mounts, payloads, editing grants and rendering. CREW can keep source retrieval, analysis and deliverables in one room. |
| **Strengths** | A foundation for trustworthy execution: scoped access, approval paths, durable artifacts and tool-grounded speech. | Successful `tools_used` grounds claims; approved actions return real destination results. Financial snapshots and calendar confirmation cards make results referenceable and reviewable. Controls still depend on each action's implementation. |
| **Strengths** | Concrete bridges already provide useful patterns to extend. | Email-to-calendar planning, Scribe-to-Media source links/import and financial calculation/snapshot surfaces provide implemented handoffs, rather than relying only on a conceptual architecture. |
| **Weaknesses** | Workflow reliability trails the breadth of the catalog. | Most recipes are compositions of tools, not dedicated end-to-end workflows. Missing mappings or action access can stop an agent after a successful source read. The observed email/calendar conversation demonstrated this failure. |
| **Weaknesses** | Recovery and handoff semantics are fragmented. | There is no universal typed handoff, cross-provider transaction or duplicate-create recovery contract. A successful first step followed by a failed write can leave partial state; prose alone cannot resolve it. |
| **Weaknesses** | Discovery and configuration do not prove readiness. | Skill/tool registration does not establish execution, credentials or applicable scopes. The Capabilities page needed an organization-scoping correction; missing schema migrations made intact chat records appear absent. |
| **Weaknesses** | Forecast coverage and confidence have material limits. | The QuickBooks scheduled-cashflow preview excludes future sales, payroll, tax, financing and overdue commitments; prediction confidence is explicitly heuristic and uncalibrated. It must not be presented as a complete financial forecast. |
| **Opportunities** | Productize a small set of dependable outcome recipes. | Make email → event, books → forecast → comparison/report, and script → production repeatable templates with explicit inputs, checkpoints and success criteria. These extend existing bridges. |
| **Opportunities** | Make capability discovery contextual and actionable. | Show each room's actual tools, connected scopes, selected skills, project bindings and blockers. Agents can ask for the one missing input or permission instead of requesting already verified facts. |
| **Opportunities** | Turn verified one-off work into repeatable operations. | Reuse reviewed artifacts in Flow jobs and App interfaces with explicit schemas, versioned sources, idempotency and regression scenarios. Financial snapshots provide a pattern for compatible period comparisons, not a universal snapshot implementation. |
| **Threats** | External service failures can interrupt an otherwise valid workflow. | Provider quota/rate limits, unavailable services, expired authorization and changed external schemas can break a multi-step chain. Execution status and resumable checkpoints must expose which step actually completed. |
| **Threats** | Ambiguous data can produce plausible but incorrect actions. | Wrong identifiers, stale source revisions, date/time-zone ambiguity and incompatible currencies/periods can yield the wrong event or financial answer. Preserve provenance and validate destination inputs before writing. |
| **Threats** | Consequential duplicates, unauthorized reach and injected source instructions can damage trust. | Retry-after-unknown-outcome may duplicate external records; a broader credential or malicious document can distort an action. Existing approval and organization boundaries must remain effective across every handoff. |

**Priority order**

1. **Reliability first:** standardize a persisted handoff envelope with source IDs/revisions, destination, scope, extracted values, remaining steps, approval state and actual outcome. Require explicit partial-failure status and action-specific duplicate checks before retrying uncertain creates.
2. **Prove the main journeys:** exercise email → calendar, financial source → forecast → saved comparison, and Scribe → Media across refresh, missing scopes, ambiguous inputs, failure after approval and retry. Component/conformance tests cannot substitute for these scenarios.
3. **Expose readiness:** show credentials/scopes, offered tools, applicable skills and missing prerequisites in CREW; detect database/schema incompatibility before it produces an empty-looking room.
4. **Then broaden automation:** promote verified recipes into Flow/App templates, with calibrated forecasting where supported and explicit exclusions where it is not.

**Strategic conclusion:** CREW's strongest asset is the shared workspace and execution/governance foundation. Its main constraint is reliable continuity between steps. Improving those transitions should precede adding more disconnected tool or studio surface area.

Room capability preflight increment: the Supervisor rail includes an on-demand Capabilities panel using the same tool resolver as CREW turns, with the currently selected studio context (or the persisted context when no selection is supplied). It lists offered tools and unavailable card declarations. The endpoint authorizes the room and Project Space before reading members, excludes foreign or disabled cards, and checks applicable Gmail and Calendar credentials in the room's organization/project scope. Credential preflight is distinct from successful provider execution; secrets and raw provider errors never appear in the report. Other integration credentials, selected skills and end-to-end recipes are explicitly not checked. Agents receive standing guidance to validate destination inputs, preserve successful source work after a blocked handoff, and request only evidenced missing inputs or access. This increment is not comprehensive readiness for every integration.

Financial and project readiness increment: the room panel now checks the caller's Account, Invoice and Bill finance permissions with the same role service used by QuickBooks cashflow execution. Company configuration is distinguished from unverified OAuth/provider availability. Project resources list only scoped binding kind, key and display name; a binding is configuration, not verified provider reach. Email/calendar and books/forecast/snapshot recipes show each agent's missing tools rather than implying that a union of room tools completes a coordinated handoff. The read-safe get_crew_readiness tool is offered to CREW agents and uses the exact tool names from the current speaking turn. It refuses absent or mismatched organization/room/project execution context and foreign or disabled membership. Other integrations, selected skills, source revisions and end-to-end success remain explicitly unverified.

Scoped inventory and skill readiness increment: CREW readiness lists all connectors visible to the room's organization/project using the canonical adapter inventory. It exposes only platform, scope, configured status, last sync and schema capture time; raw connection configuration and URLs are excluded. Inventory load failures are reported as blockers, never as evidence of no connections. Active skill augmentation records are loaded per organization/card, with missing tools computed against actual offered tools; rolled-back augmentations and rollback snapshots are excluded. Applied capabilities do not prove that a skill was selected or executed in this turn. Provider access beyond the existing Google preflights, live external schema validation and universal skill-selection receipts remain unverified.

Per-turn guidance provenance increment: generated CREW speaker turns persist a versioned crew_guidance_receipt alongside artifacts. It records platform-owned procedures actually appended to the prompt, their selection reasons and SHA-256 content hashes, without claiming execution in tools_used. Workflow readiness and currency display/arithmetic rules remain standing guidance; detailed financial reference procedures are selected for financial requests, active topics or recent financial artifacts. The transcript exposes the receipt as Guidance loaded and explicitly distinguishes prompt loading from successful execution. Imported executable skill code is not loaded as trusted instructions or executed by this selector. Applied skill augmentations remain a separate readiness view; universal imported-skill selection/execution receipts are still outstanding.

Imported contract selection and evidence increment: CREW selects up to three relevant contracts from active, organization/card-scoped augmentations whose matching review is approved or augmented and has a reviewer and review timestamp. Selection ranks request/active-topic terms against approved contract metadata, and records review/augmentation/skill IDs, reviewed time, a SHA-256 metadata-contract hash and required/missing tools. Raw imported persona instructions and executable code are excluded from the prompt; the metadata is explicitly descriptive source data. Normal tool input, credential and approval gates remain authoritative. Persisted imported-skill receipts distinguish missing mappings, reference-only contracts, no calls, partial evidence, latest tool failures and required-tool evidence; source-to-snapshot post-insert calls update the receipt. The transcript exposes selection and actual calls without asserting whole-workflow completion. Selection read failures are distinct from no matching skill. This is metadata-contract orchestration, not an arbitrary imported-code runtime or universal cross-provider recovery system; per-input provenance and outcome-specific success criteria still need dedicated recipe contracts.

Room operation export increment: successfully executed email-to-Google-Calendar confirmation cards offer Export as skill draft. The authorized room endpoint requires a same-organization approval record, a succeeded provider outcome with event ID, a typed succeeded source workflow in the same room/project, matching canonical approved argument hash, and a recorded successful proposal tool artifact. It derives an allowlisted parameterized template, not transcript instructions. The draft includes inputs, tool steps, scopes, mandatory human approval, success checks, duplicate/unknown-outcome recovery rules and proposed regression scenarios. Private source contents, event details, attendee addresses, credentials and fixed source/destination IDs are omitted; an aggregate evidence fingerprint preserves provenance. The draft is stored alongside the source turn under a row lock and deduplicated by fingerprint. It can be reviewed and downloaded as SKILL.md or a JSON contract after reload. Export neither registers nor activates a skill, nor runs the listed regressions. Other room operation types and reviewed activation remain outstanding.
